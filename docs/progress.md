# 작업 현황

CLAUDE.md가 이 파일을 불러오므로, Claude Code는 세션을 시작할 때마다 이 파일을 읽는다.
어느 PC에서 받아도 여기서부터 이어서 작업할 수 있게, **지금 상태만 짧게** 적는다.
끝난 작업의 자세한 내용은 `docs/history.md`(작업 이력)에 쌓는다.

사용자의 요청과 의도는 가능하면 사용자의 말 그대로 적는다. 사용자가 말하지 않은 의도는 짐작해서 쓰지 않는다.

마지막 갱신: 2026-10-18

작업 도중 다른 PC로 옮길 때는 여기에 어디까지 했고 무엇이 남았는지 적은 뒤, 빌드가 되는 상태로 커밋해서 push한다.

## 결정 기록

사용자가 정한 것이다. 바꿔야 하면 먼저 묻는다.
각 결정에는 이유를 붙인다. 사용자가 추천안을 골랐으면 "추천 수용"이라고 표시하고, 이유를 모르면 "기록 없음"이라고 쓴다.

- **작업 기록:** 지금 상태는 이 파일에, 끝난 작업은 `docs/history.md`에 적는다.
  - 의도(사용자): "푸시 후에 다른 피시에서 이를 받아 작업을 이어해도 문제 없도록 작업 현황이나 맥락을 기록"
  - 의도(사용자): "작업 이력을 쌓고, 진행 중인건 기록"
  - 의도(사용자): "이력과 진행상황 기록 시 내 의도도 함께 기록"
- **실행 취소 방식:** 명령마다 결과 문서를 보관한다(이전 상태 보관), 최대 50단계. 문서·레이어·타일은 바꾸지 않고, 바뀌지 않은 부분은 이전 상태와 공유한다.
  - 이유(추천 수용): 명령마다 되돌리기 코드를 따로 짤 필요가 없어 실수가 적다. 매번 전체 이미지를 복사하지 않고 바뀐 타일만 메모리를 쓴다. 나중에 '작업 내역 브러시'에 그대로 쓸 수 있다(CLAUDE.md 4장).
- **원본 픽셀:** 편집은 원본 해상도에 바로 적용한다(A). 원본 픽셀은 자바 힙 밖에 타일로 두고, 화면에는 축소본(프록시)을 그린다. 원본 해상도 계산은 바뀐 타일만 한다.
  - 이유(추천 수용): 확대해서 원본 픽셀을 보며 다듬는 고급 사용자 편집에 맞다. B(축소본을 편집하고 내보낼 때 다시 적용)는 원본 크기 계산을 내보내기로 미룰 뿐이다. 바뀐 타일만 새로 만드는 지금 엔진과 작업 내역 브러시에도 잘 맞는다.
  - CLAUDE.md 4장과 기획서의 메모리 문장을 이에 맞게 고쳤다.
- **사진 불러오기:** 8비트 sRGB로 불러온다. 넓은 색 영역의 아주 진한 색은 조금 줄고, HDR 사진의 밝기 정보(게인맵)는 버린다.
  - 50MP보다 크거나 기기 메모리로 원본이 무리면 선택 창(원본 크기 / 줄여서 / 취소)을 띄운다. 메모리가 모자라면 '원본 크기'를 끈다.
  - 줄일 때는 1/2·1/4처럼 반씩 줄인다(200MP → 50MP, 108MP → 27MP).
  - 이유: 선택 창은 사용자가 정했다("원본으로 열지 줄일지 선택지 주기"). 나머지는 계획 승인(추천 수용): 1단계 범위이고, 16비트로 담으면 메모리가 두 배다. 반씩 줄이면 해독할 때 바로 줄어 메모리가 덜 튄다.
- **타일 나누기는 CPU 복사:** 해독한 사진을 타일로 나누는 일은 안드로이드 내부 복사로 한다. Kotlin으로 픽셀을 하나씩 도는 계산이 아니라서 CLAUDE.md 2장의 'CPU 픽셀 반복 금지'에 해당하지 않는다고 본다. 축소본 그리기는 GPU로 한다.
  - 이유: 계획 승인(추천 수용)
- **회전·뒤집기·자르기는 안드로이드 내부 복사:** 픽셀 값은 그대로 두고 자리만 옮기는 일이라, GPU가 아니라 안드로이드 내부 복사(소프트웨어 그리기)로 한다. 크기 변경처럼 픽셀을 다시 계산하는 일은 GPU로 한다.
  - CLAUDE.md 2장 'GPU 우선'과 다르게 하는 것을 사용자가 승인했다(2026-10-17, 추천 수용).
  - 이유: GPU는 값이 1/255씩 달라질 수 있어(에뮬레이터에서 확인), 여러 번 돌리면 원본과 달라진다. Kotlin으로 픽셀을 하나씩 도는 계산이 아니다('타일 나누기는 CPU 복사'와 같은 방식).
- **안드로이드 부분 테스트:** 엔진에서 안드로이드에서만 도는 부분은 app 모듈의 에뮬레이터 테스트(`app/src/androidTest`)로 확인한다.
  - 이유(추천 수용): 테스트 라이브러리가 이미 있어서 새 라이브러리가 필요 없다.
- **편집 화면 도구 배치:** 기능이 생기기 전까지 모두 비활성으로 두고, 2·3단계 도구(반창고·제거 등)는 숨긴다.
  - 왼쪽 도구 막대: 자르기·변형(자르기 / 회전·뒤집기 / 크기 변경을 묶고 삼각형 표시), 브러시, 지우개, 텍스트
  - 패널: 레이어·조정. 메인 세로는 아래 접이식 패널의 탭, 메인 가로는 오른쪽 패널에 위아래로 함께(CLAUDE.md 6장)
  - 커버 화면 탭 줄: 위 6개 모두(짧은 이름)
  - 이유(추천 수용): CLAUDE.md 8장 1단계 기능에 맞춘 묶음이다.
- **테이블탑 배치:** 이번 레이아웃 작업에서 빼고 나중에 만든다.
  - 이유(추천 수용): 기획서에는 있지만 CLAUDE.md 표에는 없고, 지금은 도구가 비활성이라 위·아래로 나눠도 확인할 것이 적다.
- **작업 순서:** 테이블탑 배치와 큰 사진 조각 해독은 다른 작업을 모두 마친 뒤 맨 마지막에 한다(2026-10-17).
  - 사용자: "테이블탑 배치, 큰 사진 조각 해독는 우선순위를 작업 완전 마지막에 두세요."
  - 이유: 말하지 않음
- **아이콘 출처:** Google 공식 Material Icons(Apache 2.0)에서 받아 Vector Asset과 같은 형식으로 넣는다. Material Icons에 없는 것은 Material Symbols에서 쓴다(지우개: ink_eraser).
  - 이유(추천 수용): 지금 아이콘과 같은 출처다.
- **새 캔버스:** 프리셋은 넉넉한 크기(1:1 3000×3000, 4:5 2400×3000, 9:16 2160×3840, 16:9 3840×2160, 3:2 3600×2400, 4:3 4000×3000)와 폴드8 커버·메인 배경화면(기획서의 화면 해상도 1248×1972, 1848×2448)이다. 배경은 흰색(기본)·검은색·투명이다.
  - 이유(추천 수용): 확대해서 다듬거나 인쇄해도 선명하고, 내보낼 때 줄일 수 있다. 빈 캔버스는 메모리를 거의 쓰지 않는다. 배경색을 직접 고르는 기능은 브러시 색 고르기를 만들 때 더한다.
  - 크기 한도는 각 변 1~16383px, 전체 50MP 이하다. 이유: 계획 승인. 16383은 WebP로 내보낼 수 있는 최대 크기이고, 50MP는 사진을 선택 창 없이 여는 상한과 같다.

## 설계 메모

해당 작업을 할 때 지킨다.

- **자동 저장:** `ProjectLibrary`(앱 전체에서 하나)가 저장·불러오기·지우기를 한 번에 하나씩 한다. 저장은 앱 전체 범위에서 돌아 편집 화면이 사라져도 끝까지 한다.
  - `EditorViewModel`은 사진을 열거나 새 캔버스를 만들면 새 프로젝트로 저장하고, 편집 뒤 1.5초 멈추면·닫을 때·onStop에 저장을 부탁한다.
  - 열린 프로젝트 번호는 `SavedStateHandle`(KEY_PROJECT)에 있다. 백그라운드 종료 뒤 되살리면 ViewModel이 그 프로젝트를 다시 연다.
  - 사진 주소(URI)가 아니라 타일 픽셀을 저장한다(사진 선택기 권한은 앱이 멈추면 사라진다). 값은 `copyPixelsToBuffer`·`copyPixelsFromBuffer`로 그대로 옮긴다.
  - 새 레이어 속성(보정 값 등)은 목차의 레이어 덧붙임(꼬리표)에, 새 레이어 종류(텍스트 등)는 내용 종류 코드에 더한다. 읽는 쪽이 모르는 덧붙임은 건너뛰고, 모르는 내용 종류는 판을 올린다.
- **저장 형식:** `BlendMode`는 순서(ordinal)나 이름이 아니라 고정된 코드 값으로 저장한다.
- **내보내기:** 엔진(`ImageExporter`)이 문서를 내보낼 크기의 비트맵 한 장으로 그리고(`render`) 압축한다(`RenderedImage.writeTo`). 앱(`ExportStorage`)이 갤러리 항목과 공유 파일을 만든다.
  - 그리기는 크기 변경의 묶음 그리기(`ImageResizer.renderBlock` → `PreviewRenderer.renderRegion`)를 쓴다. 혼합 모드를 축소본에 더하면 내보내기에도 같이 들어간다. 원본 크기 레이어 하나를 그대로 베끼는 길은 혼합 모드와 상관없다.
  - 사진 정보(EXIF)를 넣게 되면, 사진을 열 때 읽어 두고 자동 저장 형식에도 보관해야 한다.
  - 설정 화면(7번)의 '기본 내보내기 형식'은 `EditorViewModel.exportChoice`의 처음 값으로 쓰면 된다.
- **편집 흐름:** 화면은 명령만 보낸다(`onEdit`). `EditorViewModel.edit`이 누르는 순간 바쁨(`Ready.busy`)을 켜고, 축소본 잠금 안에서 백그라운드로 계산한 뒤 메인 스레드에서 기록한다(`EditHistory.commit`).
  - 바쁜 동안 다른 편집·실행 취소는 무시한다. 두 손가락 보기는 된다.
  - `Ready.revision`은 보이는 문서가 바뀔 때마다 는다. 화면의 도구 상태(자르기 테두리 등)는 이것을 열쇠로 새로 시작한다.
- **도구 옵션:** 고른 도구는 `ToolSelection`(편집 화면 맨 위, `rememberSaveable`)이 든다. 옵션 자리는 커버는 캔버스와 탭 줄 사이, 메인 세로는 아래 패널(도구를 고르면 펼침), 메인 가로는 오른쪽 패널 맨 위다.
  - 도구 버튼의 길게 누르기는 `Modifier.longPressFirst`로 읽는다. M3 버튼·탭은 안쪽 클릭이 먼저 터치를 가져가기 때문이다.
  - 캔버스 위에 겹치는 도구 화면(자르기 테두리 등)은 `CanvasViewport`의 `overlay`에 넣는다. 두 손가락 감지를 가진 부모 안이라 확대·이동이 막히지 않는다.
- **레이어 패널:** 선택한 레이어는 ViewModel에 둔다. 실행 취소·다시 실행 뒤에는 그 레이어가 아직 있는지 확인한다.
- **슬라이더:**
  - 끄는 동안에는 `command.applyTo(history.document)` 결과만 보여 주고 기록하지 않는다.
  - 손을 떼면 편집 흐름(`EditorViewModel.edit`)으로 한 번 기록한다.
- **실행 취소 기록 메모리:** `EditHistory`는 단계 수(50)와 메모리 한도(`maxBytes`, 기기 메모리의 1/8)를 함께 지킨다. 타일은 객체 기준으로 한 번씩 센다.
  - 무거운 편집은 늘어날 메모리를 어림해(`CancellableCommand.estimateNewBytes`) 모자라면 오래된 단계부터 버리고(`EditorViewModel.makeRoom`), 그래도 모자라면 알리고 하지 않는다. 브러시도 이 흐름을 쓴다.
- **타일 메모리:** 레이어가 많아지면 쓰지 않는 타일을 앱 저장 공간으로 내보내 메모리를 아낀다. 레이어·브러시 작업 때 만든다.
- **큰 사진 조각 해독:** 사진을 띠 모양 조각으로 해독하면(`BitmapRegionDecoder`) 해독기 한도를 피하고, 여는 순간 메모리(지금 해독본의 2.5배)도 줄어 200MP 원본을 열 수 있다. EXIF 방향은 직접 돌려야 한다.
- **축소본:** `PreviewRenderer`가 화면 크기에 맞는 1/2^k 단계로 GPU에서 그린다. 지금은 표준 합성과 불투명도만 쓴다. 혼합 모드는 레이어 합성 작업 때 여기에 더한다.
  - 확대해서 보면 ViewModel이 보기가 0.15초 멈춘 뒤 보이는 곳(1/8 여유)을 알맞은 단계로 다시 그린다(`renderRegion`, `Ready.detail`). 그리는 일(전체·부분)은 잠금으로 한 번에 하나만 한다.
  - 편집·실행 취소로 문서가 바뀌면 전체 축소본을 다시 그리고, 부분 그림은 버린 뒤 다시 그린다(`EditorViewModel.showPreview`). 브러시처럼 작은 편집은 바뀐 타일만 다시 그리는 방법을 그때 정한다.
- **캐시:** 썸네일·GPU 텍스처는 `LayerId`가 아니라 `Raster`·`Tile` 객체를 기준으로 한다. 실행 취소 뒤 레이어 번호가 다시 쓰이기 때문이다.
- **힌지 피하기:** 패널 내용(레이어 목록·슬라이더)이나 버튼을 새로 넣을 때도 힌지를 피한다.
  - 창(대화상자)은 `AlertDialog`·`Dialog` 대신 `HingeAwareDialog`를 쓴다. 화면 전체를 덮는 자리(Box의 마지막 자식)에 둔다.
  - 세로로 쌓으면 `HingeAvoidingColumn`, 두 개를 나란히 두면 `HingeSplitRow`, 구석에 하나를 두면 `HingeAvoidingTopStart`(`ui/layout/HingeAwareLayouts.kt`)를 쓰거나 같은 방식으로 만든다.
  - Compact(커버) 배치는 힌지를 보지 않는다.
  - 메인 세로에서는 창이 접히는 선 위쪽 절반(Pixel_Fold 에뮬레이터 약 380dp)에 들어간다. 창 내용은 짧게 하고, 칸에 대한 안내는 칸 바로 위에 둔다. 키보드가 열리면 창이 낮아지고 고치는 칸이 보이게 스크롤되기 때문이다(크기 변경 창).
  - 폴드8 실기기(2026-10-17 사용자 기기에서 확인): 펼친 기본 방향은 2448×1848 창의 가운데(x=1224)를 지나는 세로선(메인 가로, Expanded), 돌리면 1848×2448 창의 가운데(y=1224)를 지나는 가로선(메인 세로, Medium)이다. 두께 0(FLAT)이고 Pixel_Fold 에뮬레이터와 방향이 같다. 접으면 없다.
- **타일 공유:** 한 가지 색 새 캔버스는 타일 한 장을 모든 자리(최대 약 800자리)가 함께 쓴다(`Raster.filled`).
  - 메모리 한도·타일 내보내기·저장 형식은 타일을 자리가 아니라 객체 기준으로 센다.
  - 끝 자리 타일의 캔버스 밖 부분은 읽지 않는다. 캔버스를 키우는 작업은 그 부분을 비우고 쓴다.
- **캔버스 표시:** `CanvasImage`가 보기 상태(`CanvasView`: 맞춤·자유)의 변환대로 체크 무늬 → 전체 축소본 → 부분 그림 → 테두리를 그린다. 보이는 픽셀만 그린다.
  - 보기 상태는 화면 쪽(`CanvasViewState`, `rememberSaveable`)이 들고, 엔진 쪽에는 `Viewport`(배율·보이는 문서 영역)만 알린다.
  - 화면 회전(다음 후보)은 `CanvasView.Free`에 각도를 더하고, `ViewTransform`과 보이는 영역 계산이 회전을 다루게 바꾸는 일이다.
- **한 손가락 도구:** 두 손가락 조작은 도구보다 먼저(Initial 단계) 읽고, 시작되면 손가락을 모두 뗄 때까지 터치를 소비한다(`CanvasGestures.kt`). 브러시 같은 도구는 소비된 터치를 보면 하던 동작을 멈춘다.
- **홈 최근 프로젝트:** `RecentProjectsGrid`(`LazyVerticalGrid`)는 위쪽 고정 영역 아래에서만 스크롤한다. 세로 스크롤 `Column` 안에 넣으면 높이가 무한대라 오류가 난다.
  - 세로 힌지: 칸마다 실제 창 위치를 재서(`onGloballyPositioned`) 띠에 걸리는 쪽 안쪽 여백을 준다(`insetsAvoiding`). 칸 너비로 어림하면 격자의 픽셀 나눔과 몇 픽셀 어긋난다.
  - 가로 힌지: 스크롤하는 카드는 지나갈 수 있다(결정 기록 '홈 최근 프로젝트'). 위쪽 버튼·제목은 피한다.

## 기술 주의점

- material3 1.4.0의 `TopAppBar`는 `@OptIn(ExperimentalMaterial3Api::class)`가 필요하다. 매개변수 타입 `TopAppBarScrollBehavior`가 실험 기능이기 때문이다.
- 아이콘은 Android Studio 'Vector Asset'의 Material Icons 파일을 쓰고, `android:tint="?attr/colorControlNormal"` 줄은 뺀다. 이 프로젝트에는 AppCompat이 없어서 그 줄이 있으면 빌드가 실패한다.
- `List.removeFirst()`·`removeLast()`는 안드로이드 13·14 기기에서 오류가 나므로 `removeAt(0)` 등을 쓴다.
- Gradle 9.6은 JDK 25로 실행한다. PC의 기본 java가 오래되었으면, 명령마다 `JAVA_HOME`을 Android Studio 내장 JDK(`jbr` 폴더)로 지정한다.
- API 37부터 `ImageDecoder`는 사진 하나를 푸는 데 약 0.5GiB(536,900,000바이트)까지만 쓴다.
  - EXIF로 돌려 보여 주는 사진은 같은 크기의 임시 버퍼를 하나 더 쓰고, 그것도 한도에 들어간다.
  - 한도를 바꾸는 `setAllocationLimit`은 SDK 소스에는 있지만 공개 SDK(android.jar)에는 없어 앱이 쓸 수 없다.
  - 그래서 8비트 사진은 약 134MP(회전이면 약 67MP)보다 크면 원본 크기로 못 연다(`ImportSizing.decodeBytes`, `PhotoImporter.decodeLimitBytes`).
- `Bitmap.createBitmap(원본, x, y, w, h)`는 바꿀 수 있는 비트맵을 돌려준다. 비트맵을 바꿀 수 없게 하는 공개 함수가 없으므로, 바꿀 수 없는 복사본은 `copy(ARGB_8888, false)`로 만든다(메모리가 없으면 null).
- `Bitmap.createBitmap(Picture, …, HARDWARE)`는 null이 아니라고 적혀 있지만, GPU가 실패하면 null을 돌려줄 수 있다.
- `connectedDebugAndroidTest`는 앱 설치에 실패해도 `BUILD SUCCESSFUL`로 끝날 수 있다. 결과 XML의 테스트 수로 확인한다(`docs/emulator.md`).
- 비트맵을 반 크기로 그릴 때 홀수 크기면 끝 픽셀이 반만 덮여 투명하게 빠진다. `PreviewRenderer.drawScaled`처럼 셰이더(CLAMP)로 올림한 크기를 채운다.
- material3 1.4.0의 `ModalBottomSheet`도 `@OptIn(ExperimentalMaterial3Api::class)`가 필요하다. 내용이 화면 반보다 길면 반만 펼쳐지므로 `skipPartiallyExpanded = true`로 연다.
- M3 `Surface`는 자기 아래 형제에게 가는 터치는 막지만, 부모의 터치 처리는 막지 않는다. 바깥을 눌러 닫는 바탕은 카드의 부모가 아니라 형제로 깐다(`HingeAwareDialog`).
- Compose 화면 테스트는 Espresso 3.7.0 이상이 필요하다. 3.5.1은 API 37에서 없어진 `InputManager.getInstance`를 불러, 화면 테스트가 모두 바로 실패한다.
- 화면 테스트의 화면 크기는 `DeviceConfigurationOverride.ForcedSize`로 정한다. 정한 크기가 기기 화면보다 크면 밀도를 낮춰 맞추므로, 테스트에서 dp를 픽셀로 바꿀 때는 노드의 밀도(`layoutInfo.density`)를 쓴다.
  - 화면 루트(`onRoot`)는 강제 크기 바깥이라 기기 밀도 그대로다. 강제 크기 안쪽 노드의 밀도를 쓴다.
- `Paint()`·`Paint(0)`에도 비트맵 필터가 켜져 있다(SDK의 HIDDEN_DEFAULT_PAINT_FLAGS). 픽셀을 그대로 옮기려면 필터·안티에일리어싱을 끄고 SRC로 그린다(`CanvasTileComposer`).
- Picture에 기록한 뒤 `Bitmap.createBitmap(picture, w, h, ARGB_8888)`으로 그리면 소프트웨어로 그려지고, 바꿀 수 없는 비트맵이 나온다.
- 화면 테스트에서 누르거나 글자를 넣은 직후에는 화면이 아직 다시 그려지지 않았을 수 있다. 화면을 찍기 전에 `waitForIdle`을 부른다.
- 화면 테스트의 `performClick`은 노드의 보이는 부분을 누른다. 키보드가 열려 창 내용이 스크롤되는 등으로 노드가 다 가려지면 엉뚱한 곳(창 왼쪽 위)이 눌렸다. 그때는 `performSemanticsAction(SemanticsActions.OnClick)`을 쓴다.
- `Bitmap.compress`:
  - JPEG는 알파를 미리 곱한 값을 그대로 써서 투명한 곳이 검게, 반투명한 가장자리가 어둡게 된다. 그래서 JPEG는 흰 바탕 위에 합성한다(`ImageExporter`).
  - 압축기는 비트맵 말고도 메모리를 더 쓴다(JPEG 픽셀당 약 3B, WebP 약 6.5B). 한 변 한도는 WebP 16383px, JPEG 65500px이다.
  - 쓰다가 난 예외는 지우고 실패(false)만 알린다. 그래서 취소였는지 따로 확인한다.
- 하드웨어 비트맵은 소프트웨어 캔버스에 그릴 수 없다(예외). GPU로 그린 것은 `copy(ARGB_8888, false)`로 읽어 온 뒤 쓴다.
- 갤러리(MediaStore)에 넣을 때는 다 쓸 때까지 IS_PENDING=1로 둔다. 쓰는 중인 항목은 약 7일 뒤 저절로 지워진다. 권한은 필요 없다.
- FileProvider는 매니페스트에 그대로 쓰지 말고 작은 하위 클래스로 쓴다(`ShareFileProvider`). 공유 창은 앱이 화면에 있을 때(STARTED) 띄운다.
- 폰을 무선 디버깅으로 연결해 두면 기기가 둘이 되어, adb 명령은 기기를 골라야 한다(`adb -s emulator-5554 …`). `connectedDebugAndroidTest`도 연결된 모든 기기에서 돈다.
  - 에뮬레이터에서만 돌리려면 `ANDROID_SERIAL=emulator-5554`를 붙인다. AGP가 이 환경 변수로 기기를 고른다(라이브러리 안에서 확인, 아직 실제로 써 보지는 않았다).
- `EditorViewModel`은 `(Application, SavedStateHandle)` 생성자를 쓴다. 안드로이드의 기본 ViewModel 공장이 이 생성자를 고른다. 테스트용으로 `(Application)` 생성자를 따로 둔다.
- Pixel_Fold 에뮬레이터는 화면이 둘이라 `adb exec-out screencap -p`에 `-d <화면 번호>`를 준다(`adb shell dumpsys SurfaceFlinger --display-id`).
- 화면 테스트에서 화면 읽기 동작을 이름으로 부르는 `performCustomAccessibilityActionWithLabel`은 실험 기능(`ExperimentalTestApi`)이다.
- 화면 테스트에서 노드의 `layoutInfo.coordinates`는 모든 Modifier 안쪽, 곧 눈에 보이는 부분이다. Material 버튼의 48dp 최소 터치 영역은 그 바깥이므로, 힌지 검사는 `touchBoundsInWindow`로 48dp까지 넓혀 본다(`HingeAssertions.kt`).

## 확인 방법

- 빌드·테스트: `./gradlew assembleDebug test`
- 화면은 에뮬레이터에서 아래를 확인한다. 에뮬레이터 만들기와 명령·요령은 `docs/emulator.md`에 있다.
  - 홈 → 편집 → 뒤로
  - 접기·펼치기(Pixel_Fold): 커버(Compact)·안쪽 기본 방향(Expanded)·안쪽 돌린 방향(Medium), 힌지 정보는 `adb logcat -s WindowHinges`

  - 편집: 회전·뒤집기·자르기·크기 변경 뒤 실행 취소·다시 실행, 큰 사진의 처리 중 표시
  - 내보내기: 갤러리 '사진/Stratum'에 생긴 파일의 크기·형식(adb pull로 꺼내 확인한 뒤 지운다), 공유 창
  - 가로 화면
  - 한국어 문구
  - 캔버스 확대·이동: 두 손가락 조작은 adb로 흉내 내기 어려워 화면 테스트(`CanvasViewportTest`·`CanvasSharpenTest`)로 본다. 부분 그림은 `adb logcat -s EditorViewModel`의 "Detail level" 줄로 본다.
